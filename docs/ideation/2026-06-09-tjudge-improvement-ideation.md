# Ideation: Улучшение и развитие TJudge

## Codebase Context

Сводка глубокого скана (4 параллельных ридера: документация/архитектура, backend, frontend, тесты/CI/ops; ключевые факты дополнительно проверены вручную grep'ами):

**Сильные стороны.** Чистая слоистость (handlers → domain → repos, интерфейсы на стороне потребителя), доменная шина событий + Redis-мост, WFQ-очередь с dedup и dead-letter, образцовый Docker-sandbox исполнения матчей (network none, CapDrop ALL, readonly rootfs, seccomp/AppArmor), ~1600 тестов на бэке, зрелый WS-хук на фронте, blue-green деплой, продуманные SLO.

**Подтверждённые проблемы:**
- Компиляция чужого кода на хосте API без таймаута: `program_upload.go:708-762` — `exec.Command` (не `CommandContext`) для gcc/g++/go/rustc/javac; утечка файлов хоста через ошибки компилятора в `program.ErrorMessage`.
- `matchScheduler` инжектится (`cmd/api/main.go:237`), но не вызывается нигде — авто-планирование матчей при upload мертво.
- Лидерборд: `GetLeaderboard` всегда идёт fallback-CTE с OR-join (`tournament_leaderboard.go:14-17,64`), matview обновляются каждые 30с впустую (`cmd/worker/main.go:154`).
- Retry воркера иллюзорен: infra-ошибка executor'а → `failed` навсегда (`processor.go:87-94,127-140`); падение `updateRatings` — только лог (`processor.go:156-163`); события публикуются без outbox.
- Idempotency: ключ глобальный без userID (`idempotency.go:91`), in-flight маркер при не-2xx живёт 24ч.
- Генерация раунда: обе ориентации AB+BA = N*(N-1) матчей (`scheduling.go:459-490`) при «1 матч на пару» в CLAUDE.md.
- `deployments/prometheus/` не существует, но монтируется в `docker-compose.selfhosted.yml:277-278` — selfhosted-мониторинг сломан, алерты из SLO.md не реализованы.
- Бэкапы: `pg_dump` локально, retention 7д, без off-site, без PITR, restore не тестируется.
- Frontend: WS `payload: unknown` не читается — на каждое событие полный REST-рефетч + поллинг 2с (TournamentDetail :1201, :2053) и 5с (AdminPanel :377); ноль мемоизации; мега-файлы (TournamentDetail 2503 строки, AdminPanel 2164); 0 тестов (нет даже test-скрипта); рукописные типы вместо кодогена из openapi.yaml; мёртвый `tailwind.config.js`.
- CI: `npm ci`+build 8 раз за прогон без общего артефакта `web/dist`; eslint фронта не запускается; benchmark/load/performance-теги нигде не гоняются (порог регрессии 10% из SLO.md §5 не энфорсится); e2e без воркера — полный путь «upload → матч → ELO» не проверяется нигде.
- Док-дрейф: `docs/ROADMAP.md` упомянут в CLAUDE.md и docs/README.md, но не существует; CLAUDE.md заявляет миграции до 000036 при существующей 000037.

## Ranked Ideas

### 1. Асинхронная компиляция программ в Docker-песочнице
**Description:** Вынести компиляцию загруженных программ из HTTP-хендлера в Redis-очередь со статусом программы `compiling`; исполнять в том же жёстком sandbox, что и матчи; сообщения компилятора фильтровать перед сохранением в `ErrorMessage`. Первый шаг — извлечь логику из `program_upload.go` в `internal/domain/program.Service` (хендлер сейчас держит 9 repo-зависимостей). Этап 0 (немедленно): заменить `exec.Command` на `CommandContext` с таймаутом.
**Rationale:** Единственное место, где недоверенный код исполняется вне песочницы: `#include "/etc/passwd"` выводит файлы хоста в ошибку gcc, видимую пользователю; компиляционная бомба подвешивает API. Один рефакторинг закрывает утечку, DoS и блокировку HTTP-пути; sandbox и очередь уже существуют.
**Downsides:** Усложнение UX (статус compiling вместо мгновенного ответа); нужен образ с тулчейнами всех языков; cross-cutting рефакторинг самого сложного флоу.
**Confidence:** 95%
**Complexity:** High (поэтапно: Low для этапа 0)
**Status:** Implemented (июнь 2026)
**Источник:** идеи 1, 15, 25, 39 (все 4 фрейма сошлись) + 14/40 (program.Service).

### 2. Транзакционный outbox + честный retry executor-ошибок
**Description:** Таблица outbox, в которую в одной транзакции с `UpdateResult` пишутся задачи «обновить рейтинг» и доменные события; диспетчер доставляет с ретраями. Классификация ошибок executor'а: инфраструктурные (Docker daemon, timeout создания контейнера) → возврат в pending с backoff; ошибка программы → терминальный failed.
**Rationale:** Закрывает три задокументированные дыры одним примитивом: потеря рейтинга при падении `updateRatings` (сейчас только лог), потеря событий между commit и Publish, иллюзорный RetryAttempts (guard `pending→running` блокирует повтор — любой чих Docker фейлит матчи навсегда и искажает турнир).
**Downsides:** Новая таблица и фоновый диспетчер; аккуратность с порядком/дедупликацией событий.
**Confidence:** 90%
**Complexity:** Medium
**Status:** Implemented (июнь 2026)
**Источник:** идеи 2, 36, 45. Follow-up: операторская консоль dead-letter/requeue (идея 12).

### 3. Лидерборд: один путь вместо двух
**Description:** Сейчас система платит дважды: каждый запрос — дорогой CTE с `LEFT JOIN matches ON (program1_id = p.id OR program2_id = p.id)` (OR-join ломает index scan), и каждые 30с — refresh matview, которые никто не читает. Выбрать: (а) читать из matview + точечная инвалидация по `MatchResultProcessed` (event-driven refresh уже возможен — шина есть), или (б) удалить matview+refresher и оптимизировать CTE (UNION ALL вместо OR). Вариант-максимум — инкрементальный лидерборд в Redis ZSET (отложен, см. отклонённые).
**Rationale:** Лидерборд — самый горячий read-path (SLO 10ms), его бьёт и поллинг фронта, и WS-рефетчи. Комментарий в коде показывает, что fallback выбран сознательно ради актуальности — но тогда refresher чистый расход.
**Downsides:** Вариант (а) даёт устаревание до интервала refresh; вариант (б) требует EXPLAIN-проверки на реальных объёмах.
**Confidence:** 95%
**Complexity:** Low–Medium
**Status:** Implemented (июнь 2026)
**Источник:** идеи 3, 13, 44 (+32 как отложенный вариант).

### 4. Frontend: WS-payload как источник данных + TanStack Query, поллинг — только fallback
**Description:** Типизировать payload WS-событий (сейчас `payload: unknown` никогда не читается), применять обновления в кэш TanStack Query (патч или точечная инвалидация); 2-секундный поллинг включать только при `isOnline=false`. AdminPanel перевести с 4 запросов/5с на события. Попутно TanStack Query убирает ~30 ручных useState isLoading/error на страницу и даёт дедупликацию/optimistic updates.
**Rationale:** Сейчас каждая открытая вкладка турнира генерирует двойную-тройную нагрузку (поллинг лидерборда + поллинг матчей + рефетч на каждое WS-событие) — и всё это бьёт в медленный CTE из идеи 3. WS-инфраструктура (hub, Redis-мост, авторизация) уже оплачена и используется как «пинг».
**Downsides:** Рефактор крупнейших страниц (TournamentDetail 2503 строки); нужна общая схема WS-событий с бэком; осторожность с консистентностью патчей.
**Confidence:** 90%
**Complexity:** Medium
**Status:** Implemented (июнь 2026)
**Источник:** идеи 5, 17, 31, 38.

### 5. Placement-матчи против эталонных ботов + прозрачный статус программы
**Description:** Оживить мёртвый `matchScheduler`: после успешной компиляции программа автоматически играет unrated smoke-матчи против встроенных baseline-ботов (tit-for-tat, always-defect, random — классика для всех пяти игр); результат показывается команде сразу. Плюс полный жизненный цикл в UI: uploaded → compiling → ready → queued → playing → результат, через существующий WS. Низший приоритет WFQ-очереди (5:3:1) подходит для тест-матчей из коробки.
**Rationale:** Сейчас команда загружает программу и не знает, жива ли она, пока админ вручную не запустит раунд — главное трение участника и источник саппорт-вопросов к solo-оператору. Инфраструктура (executor, очередь, WS) готова; не хватает только ботов и вызова планировщика.
**Downsides:** Боты живут в tjudge-cli (внешний Rust-репозиторий); нужно понятие unrated-матча в домене.
**Confidence:** 85%
**Complexity:** Medium
**Status:** Unexplored (в бэклоге, см. docs/ROADMAP.md)
**Источник:** идеи 8, 27, 49 + 9 (прозрачность статуса).

### 6. Реплеи матчей: транскрипты итераций + страница реплея
**Description:** Научить tjudge-cli писать JSONL-транскрипт ходов (решения обеих программ и очки по итерациям) в смонтированный volume; сохранять как артефакт (storage или таблица match_transcripts); на фронте — страница реплея: график накопленных очков, лента ходов, паттерны стратегий (доля кооперации, мстительность).
**Rationale:** Для образовательной платформы по теории игр это главная продуктовая фича: сейчас участник видит «3.2 : 1.7» и не понимает, почему проиграл. Реплей превращает «судью» в инструмент обучения и даёт материал для аналитики (fingerprint стратегий, head-to-head).
**Downsides:** Изменения во внешнем Rust-репозитории; объём хранения транскриптов (нужен retention); самая дорогая из идей.
**Confidence:** 80%
**Complexity:** High
**Status:** Unexplored (в бэклоге, см. docs/ROADMAP.md)
**Источник:** идеи 7, 28.

### 7. Операционная готовность: алерты из SLO.md + off-site бэкапы + restore-тест
**Description:** (а) Создать `deployments/prometheus/prometheus.yml` + `alerts/*.yml`, дословно реализовав уже задекларированные алерты SLO.md (APIHighErrorRate, QueueStuck, DeadLetterGrowing, match pickup lag) — починит и битые volume-mounts selfhosted-стека. (б) Выгрузка бэкапов в S3-совместимое хранилище (rclone/restic), wal-g для PITR. (в) Nightly-проверка: развернуть последний дамп в чистый PostgreSQL + smoke-запросы. Попутно: retention старых партиций matches/rating_history в уже существующей горутине.
**Rationale:** Для solo-оператора без дежурного алерты — единственный способ узнать о проблеме раньше пользователей; сейчас SLO — бумага, а selfhosted-мониторинг падает на старте. Потеря диска сервера сегодня означает потерю и БД, и бэкапов; непротестированный бэкап — не бэкап.
**Downsides:** Понадобится внешнее хранилище (небольшие расходы); алерты потребуют калибровки порогов.
**Confidence:** 95%
**Complexity:** Low–Medium
**Status:** Implemented (июнь 2026)
**Источник:** идеи 4, 23 (упрощённо), 34, 42 + 11 + 19 (retention попутно).

### 8. CI-эпик: web/dist один раз, фронт-проверки, nightly full-flow, перф-гейт
**Description:** (а) Собирать `web/dist` один раз в отдельном job и шарить артефактом (сейчас npm ci+build — 8 раз за прогон). (б) Включить eslint фронта в CI + добавить vitest (@testing-library/react): готовый `schema.test.ts` оживает сразу; первые цели — refresh-mutex и retry в `client.ts`, backoff в `useWebSocket`. (в) Nightly: API+worker+Docker-executor, полный путь «регистрация → upload → матч → ELO → WS» (сейчас не проверяется нигде — именно так незаметно умер matchScheduler). (г) Перф-гейт: бенчмарки + benchstat против baseline, фейл при регрессии >10% — правило уже записано в SLO.md §5.
**Rationale:** Медленный CI — налог на каждый коммит solo-разработчика; 0 фронт-тестов при ~1600 бэкендных и непроверяемое ядро продукта (Docker-исполнение) — главные слепые зоны.
**Downsides:** Nightly с Docker потребует ресурсов раннера; baseline бенчмарков нужно осознанно поддерживать.
**Confidence:** 90%
**Complexity:** Medium
**Status:** Implemented (июнь 2026)
**Источник:** идеи 10, 35, 41, 47, 20, 43, часть 24.

### 9. Контракты как код: OpenAPI → TS-кодоген + ROADMAP.md + проверка консистентности доков
**Description:** Генерировать TS-типы и клиент из `docs/openapi.yaml` (openapi-typescript/orval) вместо рукописных `types/index.ts` и ~70 методов `ApiClient`; CI проверяет свежесть (`git diff --exit-code`). Типы WS-событий генерировать из Go-структур (tygo). Создать отсутствующий `docs/ROADMAP.md` (собрать разбросанные решения «не делать»: password-reset удалён, CSRF не активирован, PITR был отложен, K8s экспериментален) + лёгкий CI-скрипт проверки заземляемых фактов доков (число миграций, версия Go, существование файлов по ссылкам).
**Rationale:** Рассинхрон фронт/бэк становится ошибкой компиляции, а не багом в проде; каждый будущий эндпоинт дешевле. Документация уже врёт (миграции 000036 vs существующая 000037, битая ссылка на ROADMAP) — а это основной инструмент рычага и для solo-разработчика, и для AI-агентов.
**Downsides:** openapi.yaml должен стать действительно полным (contract-тесты помогут); первичная миграция клиента — заметный разовый труд.
**Confidence:** 85%
**Complexity:** Medium
**Status:** Implemented (июнь 2026)
**Источник:** идеи 18, 37, 48.

### 10. Решить судьбу AB/BA: одна ориентация на пару (потенциально −50% матчей)
**Description:** Код генерирует обе ориентации (AB и BA) — N*(N-1) матчей на раунд; CLAUDE.md заявляет «1 матч на пару». Решить намеренно: для симметричных игр вторая ориентация не добавляет информации — схлопнуть до неупорядоченных пар (или чередовать ориентацию по раундам для асимметричных игр), либо задокументировать, почему AB+BA нужны. Точка изменения одна — `generateMatches`.
**Rationale:** Docker-запуск матча — самая дорогая операция системы; халвинг удваивает пропускную способность турнира бесплатно. На 100 командах: 9900 → 4950 контейнеров за раунд. Минимум — устраняется противоречие код↔документация.
**Downsides:** Продуктовое решение: для асимметричных игр (перетягивание каната, аукцион) ориентация может иметь значение — нужно проверить семантику ролей в tjudge-cli; возможно, AB+BA сознательны.
**Confidence:** 70% (что халвинг применим; 100% — что противоречие надо разрешить)
**Complexity:** Low
**Status:** Resolved — AB/BA подтверждено намеренным, документация исправлена под код
**Источник:** идеи 16, 26 (Swiss — отложенный вариант).
